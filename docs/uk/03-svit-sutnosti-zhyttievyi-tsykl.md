# 3. Світ, сутності, життєвий цикл

`World` — це розподільник ідентифікаторів сутностей і реєстр сховищ. Він не
зберігає ігрових даних; він відповідає на питання «які сутності живі» і «які
сховища існують».

---

## 3.1. Створення світу

```swift
let world = World(entityCapacity: 10000)   // ємність: 10 000 одночасно живих сутностей
```

Ємність задається один раз, і всі внутрішні буфери виділяються **одразу**.
Світ **не росте сам** — це свідоме рішення. Прихована алокація в гарячому
циклі при десятках тисяч сутностей дає фриз на слабкому пристрої, а фриз,
який стається раз на кілька хвилин у випадковий момент, майже неможливо
відлагодити.

Якщо ємності може забракнути — читайте про явне зростання й автоматичну
політику в
[розділі 7.3](07-chas-podii-yemnist.md#73-ємність-і-політика-зростання).

### Порядок складання світу

```swift
let world = World(entityCapacity: 10000)

// 1. Спочатку ВСІ сховища.
world.registerStore(positions, typeID: ComponentType.position.rawValue)
world.registerStore(velocities, typeID: ComponentType.velocity.rawValue)
world.registerStore(enemyTag, typeID: ComponentType.enemy.rawValue)

// 2. Потім системи.
scheduler.addSystem(...)
scheduler.setupAll(world: world, context: context)

// 3. І лише тепер — сутності.
let entity = world.createEntity()
```

Схема **блокується першим `createEntity()`**: після нього
`registerStore(_:typeID:)` поверне `false` і повідомить діагностику. Це
навмисно — сховище, зареєстроване пізніше, не знало б про вже створені
сутності, і його sparse-масив був би неузгоджений.

Ідентифікатор типу (`ComponentType.position.rawValue` тощо) — будь-який
`Int32` на ваш розсуд; ідіома з [розділу 2](02-shvydkyi-start.md) —
невеликий `enum ComponentType: Int32` з одним case на тип компонента. Світ
використовує його лише для `getStore(_:)` і діагностики; на швидкість він не
впливає.

---

## 3.2. Сутність — це число

```swift
let entity = world.createEntity()
if entity < 0 {
    return            // світ заповнений — перевіряти ОБОВ'ЯЗКОВО
}
```

`createEntity()` повертає **`kInvalidEntity` (`-1`)**, коли вільних
ідентифікаторів більше немає. Це не кинута помилка — `Entity` є звичайним
типалясом `Int32`, і бібліотека ніколи не кидає винятків — це нормальний стан
переповненого світу, і викликальний код зобов'язаний його перевіряти.

Ідентифікатор — це щільний індекс у діапазоні `[0, capacity)`. Він напряму
адресує `sparseIndex` кожного сховища, тому лишається найдешевшим
представленням у гарячому циклі: жодного декодування, жодної перевірки.

### Пакетне створення

Коли за кадр народжується багато сутностей — хвиля ворогів, вибух на
частинки, поділ клітин — платити накладні витрати на кожен виклик не варто:

```swift
var ids = [Entity](repeating: kInvalidEntity, count: 256)   // один раз, наперед
let spawned = world.createEntities(64, into: &ids)
// spawned може бути меншим за 64, якщо світ майже повний
```

Далі цей самий буфер віддається сховищам:

```swift
let firstSlot = Int(positions.count)      // ЗНЯТИ ДО виклику
positions.attachMany(ids, count: spawned)
for i in 0..<Int(spawned) {
    positions.columnF32(0)![firstSlot + i] = 0.0
}
```

Нові компоненти займають слоти `[firstSlot, firstSlot + attached)` **у тому
самому порядку**, в якому сутності йшли у буфері.

## 3.3. Handle: посилання, що переживає кадри

Сирий ідентифікатор безпечний **тільки в межах структурної епохи** — тобто
доки не викликано `flushDestroyQueue()` або `reset()`. Після знищення той
самий номер може отримати інша сутність.

Тому для всього, що живе між кадрами — ціль турелі, власник ефекту, елемент
UI, відкладений колбек, зовнішня черга — існує **generational handle**:

```swift
let handle = world.makeHandle(entity)

// ...багато кадрів потому:
let current = world.entityFromHandle(handle)
if current == kInvalidEntity {
    return          // ціль загинула; handle протух
}
// тут `current` знову можна використовувати як звичайний Entity
```

`Handle` (типаляс `Int64`) — це додатне число, у яке запаковано три речі:

```
біти  0..23  сирий id сутності   (до 16 777 216 слотів)
біти 24..47  покоління (generation)
біти 48..62  тег світу
```

**Покоління** — лічильник, що зростає щоразу, коли слот звільняється. Тому
старий handle на перевикористаний слот не збігається за поколінням і буде
відхилений. Це захист від класичної **ABA-проблеми**: «те саме число, але
вже інша сутність».

Якби один і той самий слот знищувався й перестворювався достатньо разів, щоб
вичерпати 24-бітний лічильник поколінь, слот не обнуляє покоління й не йде в
повторне використання — він **виходить з обігу назавжди** (див.
`getRetiredCount()` у [розділі 3.6](#36-діагностика)). Повторне використання
переповненого покоління тихо відтворило б ту саму ABA-помилку, від якої й
захищає handle, тож бібліотека радше жертвує ємністю одного слоту, ніж
ризикує нею. Приблизно на шістнадцяти мільйонах перевикористань одного слоту
це не практична проблема майже для жодного застосунку, але надзвичайно
довготривалий світ поступово розмінює трохи ємності на цю гарантію.

**Тег світу** захищає від того, щоб handle одного світу випадково розв'язався
в іншому (актуально, якщо у вас кілька незалежних симуляцій — див.
[розділ 3.7](#37-кілька-світів)).

### Правило вибору

| Ситуація | Що зберігати |
|---|---|
| Всередині одного кадру, всередині системи | сирий `Entity` |
| Ціль, власник, підписка, UI, таймер, асинхронна робота | `Handle` |
| Збереження на диск, мережа | **власний стабільний ідентифікатор**, не handle |

Handle **не є** стабільним ідентифікатором між запусками застосунку: тег
світу видається з лічильника, спільного для всього процесу (внутрішній
`nextWorldTag` у `World`, починається з 1) і скидається до 1 при кожному
новому запуску процесу, а покоління так само специфічне для цього запуску.
Handle, записаний на диск під час одного запуску, не гарантовано розв'яжеться
в ту саму сутність — та й узагалі безпечно розв'яжеться — під час наступного.

### Допоміжні методи

```swift
world.createEntityHandle()               // створити і одразу отримати handle
world.isHandleAlive(handle)              // без розв'язання в id
world.queueDestroyHandle(handle)         // безпечне знищення за handle
world.isHandlePendingDestroy(handle)
```

## 3.4. Знищення: найважливіше правило

Ще раз, бо це те місце, де ламаються всі ECS-новачки.

```swift
world.queueDestroy(entity)     // ТІЛЬКИ позначає
world.flushDestroyQueue()      // реально знищує
```

`queueDestroy(_:)` **ідемпотентний**: якщо кілька систем у одному кадрі
незалежно вирішать убити ту саму сутність, у чергу вона потрапить один раз.

`flushDestroyQueue()` — це **structural sync point**. Він:

1. перевіряє покоління, зафіксоване поряд із кожним записом черги;
2. від'єднує сутність від кожного зареєстрованого сховища;
3. виконує swap-remove і хуки очищення;
4. позначає сутність мертвою;
5. просуває покоління (або виводить слот з обігу — див.
   [3.3](#33-handle-посилання-що-переживає-кадри));
6. і лише тоді повертає id у пул вільних.

### Де його викликати

Використовуйте готовий `ReaperSystem`, зареєстрований **останнім**:

```swift
scheduler.addSystem(MovementSystem())
scheduler.addSystem(CombatSystem())
scheduler.addSystem(ReaperSystem(world: world))    // ← остання
```

Технічно flush можна ставити на кількох явних межах фаз. Але **ніколи** —
усередині системи, і **ніколи** не можна кешувати щільний слот через цю
межу:

```swift
// НЕПРАВИЛЬНО
let slot = positions.indexOf(entity)
world.flushDestroyQueue()                  // тут swap-remove міг перемістити дані
positions.columnF32(0)![Int(slot)] = 0.0   // пишемо в чужий компонент
```

Handle лікує протухле **посилання на сутність**, але не протухлий **щільний
слот**. Слот треба брати заново після будь-якої структурної зміни.

### Пакетне позначення

```swift
world.queueDestroyMany(entities, count: entityCount)
```

## 3.5. Reset: перезапуск рівня без алокацій

```swift
world.reset()
```

Усі сутності «вмирають», усі сховища очищаються — **без жодної алокації**:
буфери просто перезаповнюються. Реєстрації сховищ зберігаються, повторно
викликати `registerStore(_:typeID:)` не треба й не можна.

`reset()` інвалідує всі активні handle: покоління кожної живої сутності
просувається (або слот виходить з обігу — за тим самим правилом, що й у
[3.3](#33-handle-посилання-що-переживає-кадри)).

## 3.6. Діагностика

```swift
world.getLiveCount()             // скільки сутностей живих
world.getFreeCount()             // скільки id лишилося
world.getRetiredCount()          // слоти з вичерпаним поколінням
world.getPendingDestroyCount()   // скільки чекає у черзі
world.getLoadFactor()            // live / capacity, у 0...1
world.capacity
world.structuralVersion          // монотонний лічильник структурних змін
```

### Перевірка цілісності

```swift
if !world.validateIntegrity() {
    assertionFailure()
}
```

Повна перевірка розподільника, черги знищення й усіх sparse-множин:
сходяться чи ні лічильники, чи немає дублікатів у списку вільних, чи
бієктивні sparse↔dense відображення, чи не прикріплений компонент до мертвої
сутності.

Перевірка **лінійна за ємністю** і створює тимчасові буфери. Це інструмент
розробки: викликайте його з тестів, з debug-панелі або у fuzz-циклі, але **не
з продакшн-кадру**.

`validateIntegrity(reportErrors: false)` не повідомляє діагностику, а лише
повертає `Bool` — зручно для тестів (див. `WorldTests.swift`).

## 3.7. Кілька світів

Нічого не заважає мати кілька незалежних екземплярів `World` — наприклад, по
одному на матч, на рівень або на паралельну симуляцію. Тег світу в handle
гарантує, що посилання одного світу не розв'яжеться в іншому.

Обмеження: тегів вистачає на 32 767 світів, створених за час життя процесу
(вони не перевикористовуються). Після вичерпання світи продовжують працювати
з сирими id, але handle-API повідомляє діагностику й повертає
`kInvalidHandle`. На практиці це недосяжна межа, якщо ви не створюєте новий
світ щокадру.

---

## Головне з розділу

1. Ємність фіксується при створенні; світ не росте сам.
2. Усі сховища реєструються **до** першої сутності.
3. `createEntity()` може повернути **`kInvalidEntity` (-1)** — перевіряйте
   завжди.
4. Сирий `Entity` — у межах кадру; **`Handle`** — між кадрами; **власний
   стабільний ідентифікатор** — у файл.
5. `queueDestroy()` позначає, `flushDestroyQueue()` знищує — **рівно в одній
   точці кадру**, зазвичай через `ReaperSystem`.
6. Не кешуйте щільний слот через структурну зміну.
