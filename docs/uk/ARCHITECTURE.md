# Архітектура Aegis ECS

Цей документ описує розширену модель Aegis для великої гри. Основний принцип
не змінився з оригінального GDScript-дизайну, з якого зроблено цей порт:
найшвидший шлях — це й досі звичайний цикл по щільних, пласких колонках.
Безпека й узагальненість додаються як окремі холодні API, тож частинка чи
снаряд не платять за можливості, якими не користуються.

Це **довідник рішень**, а не туторіал. Якщо шукаєте «як цим користуватися» —
починайте з [посібника](README.md).

## Шари

```text
World
  ├─ розподільник сирих id + відкладена черга знищення
  ├─ пакетні createEntities() / queueDestroyMany()
  ├─ generation + world tag → безпечний Handle між кадрами
  ├─ реєстр sparse-set сховищ ComponentStore
  └─ явні бар'єри ємності й перевірки цілісності

Сховища
  ComponentStore            sparse set, хуки оголошуються явно
    ├─ PackedStore          декларативно: схема ColumnType — і нічого більше
    └─ TagStore             без корисного навантаження, спеціалізоване пакетне видалення

Обхід
  ├─ прямий sparse-цикл     найшвидший, з'єднується вручну
  ├─ View                   живий фільтр без алокацій
  └─ Query                  попередньо виділений кеш складу

Виконання
  Scheduler
    ├─ порядок реєстрації — це поведінка
    ├─ перемикачі системи/фази, пропуск через requiresTime
    ├─ метадані читання/запису й аналіз конфліктів
    └─ профілювання (накопичення за кадр + згладжене середнє)

Готові системи
  ├─ ReaperSystem            єдина точка знищення
  └─ CapacityPolicySystem    вирощує світ до того, як він заповниться

Допоміжні
  ├─ SimulationClock        фіксований крок, масштаб часу, запобіжник
  ├─ UniformSpatialGrid     broadphase на counting sort, плаский режим
  └─ AngleMath              довертати кут найкоротшим шляхом

UI (окремий продукт)
  AegisECSInspectorUI
    └─ InspectorPanelView    SwiftUI-панель над Inspector — див. розділ 13
```

## Сирий id і generational handle

Сирий `Entity` (`Int32`) — це індекс від `0` до `capacity - 1`. Він напряму
адресує `sparseIndex`, тож лишається найдешевшим представленням у гарячому
циклі.

Сирий id не можна вважати стабільним посиланням через точку структурної
синхронізації. Після знищення той самий індекс може дістатися іншій сутності.
Для цілі, власника, вибору в UI, запланованого колбека й зовнішньої черги
натомість використовується додатний 63-бітний `Handle` (`Int64`):

```text
bits  0..23  сирий id сутності   (до 16 777 216 слотів)
bits 24..47  generation          (до 16 777 215 життів на слот)
bits 48..62  тег світу в межах процесу
bit      63  0
```

```swift
let entity = world.createEntity()
let handle = world.makeHandle(entity)

// Багато кадрів по тому:
let resolved = world.entityFromHandle(handle)
guard resolved != kInvalidEntity else { return }
```

Handle відхиляється, якщо не збігається тег світу, generation, діапазон або
стан «живий». При переповненні generation слот стає **retired** і більше
ніколи не видається: старий handle не може ожити навіть теоретично. Теги
світу не перевикористовуються; `World.nextWorldTag` — лічильник у межах
процесу, тож після 32 767 світів, створених за час життя процесу, нові світи
й далі працюють із сирими id, але `makeHandle`/`entityFromHandle`
повідомляють про помилку (`kInvalidHandle` / `kInvalidEntity`) замість
розв'язання.

Рантайм-handle — **не** ідентифікатор для збереження/мережі: тег світу
прив'язаний до одного запуску процесу й не стабільний між перезапусками. Між
запусками використовуйте власний доменний стабільний ключ.

## Життєвий цикл і структурні епохи

```text
FREE → ALIVE → PENDING_DESTROY → FREE
                              ↘ RETIRED при переповненні generation
```

`queueDestroy*()` не змінює жодного сховища. Позначена сутність і її handle
лишаються дійсними до `flushDestroyQueue()`. Флаш — точка структурної
синхронізації:

1. перевіряє повторно ключ із проставленою generation, записаний у чергу;
2. відкріплює сутність від кожного сховища;
3. виконує swap-remove і хуки очищення;
4. позначає сутність мертвою;
5. просуває generation (`nextGeneration`);
6. і лише тоді повертає сирий id у вільний стек — або переводить слот у
   retired, якщо лічильник generation вичерпано.

Флаш може стояти на кількох межах фаз. Він не може виконуватися посеред
системи, і жодна система не може тримати щільний слот через цю межу.
Generational handle лікує застаріле посилання на сутність, але не застарілий
щільний слот чи застарілий покажчик колонки `PackedStore`.

`reset()` робить недійсними handle усіх активних і позначених сутностей,
очищає сховища й чергу, але зберігає реєстрації та ємність. Схема
блокується першим успішним `createEntity()`; усі сховища мають бути
зареєстровані заздалегідь.

## Сховища й очищення посилань

Сховище — це sparse set із двобічним відображенням:

```text
sparseIndex[entity]  → щільний слот або -1
denseEntities[slot]  → entity
payload[slot]        → дані компонента
```

Спадкоємець завжди реалізує `reserveDense(_:)` і `relocateDense(from:to:)` —
`ComponentStore` оголошує їх як обов'язкові перевизначення, і базова
реалізація викликає `fatalError()`, якщо спадкоємець пропустив хоч одне, тож
забути щось ловиться одразу, а не тихо. Якщо payload володіє
керованим ARC ресурсом, сховище оголошує відповідні хуки:

```swift
final class OwningStore: ComponentStore {
    var resources: [SomeManagedResource?] = []

    override var hooks: Hooks { [.growDense, .releaseDense, .clearRelocated] }

    override func releaseDense(_ slot: Int32) {
        resources[Int(slot)] = nil   // ARC звільняє; вручну звільняти не потрібно
    }

    override func clearRelocatedDense(_ slot: Int32) {
        resources[Int(slot)] = nil   // володіння вже перенесено; не звільняти вдруге
    }
}
```

Detach спершу викликає `releaseDense(removedSlot)`, потім переносить останній
payload і викликає `clearRelocatedDense(lastSlot)`. Ці два не можна плутати:
інакше видалений ресурс протече (ніколи не стане `nil`) або перенесений
звільниться двічі. Без хуків власний щільний масив сховища назавжди тримає
сильне посилання на старий ресурс кожного видаленого елемента — сам по собі
ARC тут не рятує, бо тримає саме слот масиву.

`structuralVersion` змінюється при новому attach, успішному detach, непорожньому
clear і зростанні ємності. Запис payload його не змінює: склад запиту
лишається тим самим.

## Вибір між прямим циклом, View і Query

### Прямий цикл

Використовуйте у найгарячіших системах з відомою схемою. Найменше сховище
обирається драйвером, решта компонентів перевіряється через sparse-масиви.

```swift
let entities = velocities.denseEntities
let positionSlots = positions.sparseIndex
for velocitySlot in 0..<Int(velocities.count) {
    let entity = entities[velocitySlot]
    let positionSlot = positionSlots[Int(entity)]
    if positionSlot == -1 { continue }
    // ...
}
```

### `View`

`View` резолвить обов'язкові/виключені type id один раз. `refreshDriver()`
обирає найменше з обов'язкових сховищ, `matches(_:)` читає поточні
sparse-набори. Після `configure()` стійкий API не будує жодного масиву
результату й нічого не алокує.

`View` зручніший за ручне з'єднання, але `matches(_:)` лишається викликом
методу на кожного кандидата. Для найгарячіших систем візьміть sparse-масиви
з view (`requiredSparse(_:)`/`excludedSparse(_:)`) і вбудуйте перевірку в
свій цикл — саме резолвінг масивів один раз і пряма перевірка прибирають
виклик на кандидата.

### `Query`

`Query` матеріалізує id сутностей у попередньо виділений буфер. За
замовчуванням його розмір дорівнює `world.capacity`; опційний
`maximumResults` обмежує буфер для запиту з відомою верхньою межею. `Query`
відстежує `structuralVersion` кожного відстежуваного сховища й пропускає
перебудову, якщо жодне не змінилося (`isCurrent`).

```swift
if query.refresh() {
    // склад справді змінився
}
query.withEntities { buf in
    for index in 0..<Int(query.count) {
        let entity = buf[index]
    }
}
```

Перебудова піднімає кожен sparse-масив, що бере участь, у локальну змінну до
циклу і — коли перевіряти нічого, крім сховища-драйвера, — копіює напряму з
щільного масиву драйвера без жодного виклику `matches()`.

З обмеженим буфером `count` ніколи не перевищує `maximumResults`, а
`isTruncated` повідомляє, що знайдено більше сутностей. Без ліміту пам'ять
результату — приблизно `4 байти × world.capacity` на `Query` (`Entity` — це
`Int32`): 100 повних запитів при ємності 1 000 000 забрали б близько 381 МіБ.

`withEntities { buf in ... }` прибирає виклик методу на елемент, але буфер
доступний лише для читання і не повинен зберігатися через `refresh()` чи
`world.reserveCapacity()`.

`View`/`Query` вимагають хоча б один обов'язковий тип: світ свідомо не тримає
другий щільний список «усі живі» лише заради запиту без компонентів.

## Планувальник, фази й метадані

Планувальник ніколи не сортує системи. Порядок реєстрації лишається повною
специфікацією поведінки. Фаза — це фільтр і метадані:

```swift
scheduler.addSystem(InputSystem(), phase: 100)
scheduler.addSystem(MovementSystem(), phase: 200)
scheduler.addSystem(RenderUploadSystem(), phase: 300)
scheduler.addSystem(ReaperSystem(world: world), phase: 400)
```

Звичайний кадр використовує `executeAll(delta:)` — він сам викликає
`beginFrame()` першим кроком. Якщо фази викликаються з різних місць вашого
коду, закрийте попередній кадр самостійно, один раз:

```swift
scheduler.beginFrame()
scheduler.executePhase(100, delta: delta)
scheduler.executePhase(200, delta: delta)
scheduler.executePhase(300, delta: delta)
scheduler.executePhase(400, delta: delta)
```

Заміри **накопичуються** між двома викликами `beginFrame()`, тож кадр із
фіксованим кроком, що запускає фазу симуляції чотири рази, звітує про
сукупну вартість цих чотирьох суб-кроків — тобто те, що справді потрапило в
бюджет кадру. Згладжене середнє згортається раз на кадр, а не на суб-крок.

`enabled` і перемикання фаз не видаляють системи, тож індекси профайлера
стабільні. Вимкнена система отримує заміри `0` і
`wasSystemExecuted(_:) == false`.

### Пропуск через `requiresTime`

Пауза — це нульовий крок, а не пропущений кадр. Без цього кожна залежна від
часу система мала б починатися з `if delta <= 0 { return }`, і забути цей
рядок — тиха помилка. Натомість система встановлює `requiresTime = true`,
типово в `init()`, і планувальник взагалі пропускає виклик — це і безпечніше,
і уникає самого виклику.

`ReaperSystem` свідомо лишає `requiresTime == false`: сутності, позначені на
знищення до паузи, все одно мають бути прибрані, інакше вони висітимуть у
черзі й у кожному сховищі протягом усієї паузи.

### Метадані доступу

Оголошуються один раз, типово в `init()`:

```swift
_ = declareRead(ComponentType.input.rawValue)
    .declareWrite(ComponentType.position.rawValue)
    .declareStructuralWrite(ComponentType.sleeping.rawValue)
writesWorldStructure = true   // create/destroy/reset
_ = completeAccessMetadata()
```

Метадані не змінюють порядок виконання і не додають перевірок під час
`execute()`. Вони використовуються `validatePipeline(world:)`,
`validateOwnerAccess(reportErrors:)` у `View`/`Query`, та
`systemsConflict(_:_:)`. Останній консервативно відповідає, чи могли б дві
системи потрапити в майбутній паралельний батч. Доки система не викликала
`completeAccessMetadata()`, її доступ вважається невідомим і вона конфліктує
з будь-якою іншою — тож система, що не підключилася до цього механізму, не
може випадково бути визнана безпечною для небезпечного паралельного батчу.
Поточний планувальник лишається послідовним. `writesWorldStructure` завжди
конфліктує з кожною системою: create/destroy/reset змінюють дійсність сирих
id і кожного `View`, навіть для системи без власних оголошень.

`systemPhase` системи фіксується в момент, коли її призначає
`addSystem(_:phase:)` — методу для перенесення вже зареєстрованої системи в
іншу фазу немає; реєструйте під правильною фазою одразу. Один екземпляр
системи не можна поділити між двома планувальниками чи зареєструвати двічі в
одному — обидва випадки відхиляються з діагностикою.

`teardownAll()` викликає системи у зворотному порядку — ресурси
розбираються як стек відносно `setup`.

## Зростання ємності

Стійкий кадр ніколи не зростає сам. Якщо прогноз змінився:

```swift
// екран завантаження / зупинений конвеєр
world.reserveCapacity(200_000)
```

Світ і всі зареєстровані сховища зростають разом; наявні сирі id, handle і
щільні слоти зберігаються (але не закешовані покажчики колонок
`PackedStore` — перезапитайте їх після будь-якого зростання). Власні зовнішні
буфери застосунку (батч рендера, broadphase фізики, мережевий масив)
бібліотека вирощувати не може — це відповідальність коду завантаження.
`Query` адаптує свій кеш при наступному `refresh()`.

Підтримка зростання для власного сховища — опційна, оголошується явно:

```swift
override var hooks: Hooks { [.growDense] }

override func growDense(previousCapacity: Int32, newCapacity: Int32) {
    positions.reserveCapacity(Int(newCapacity))
    while positions.count < Int(newCapacity) { positions.append(0) }   // зберегти [0, count)
}
```

Окремого булевого прапорця немає: сховище підтримує зростання тоді й лише
тоді, коли оголошує `.growDense` у перевизначених `hooks`. На відміну від
оригінального GDScript-аддону — який виявляв перевизначення через
рефлексію `has_method()` під час реєстрації, бо базовий клас свідомо не
оголошував метод, — у Swift немає еквівалентної рантайм-рефлексії, тож
перевірка явна й формується на етапі компіляції:
`ComponentStore.initialize()` читає `hooks` рівно один раз і кешує результат
у `cachedHooks`, приватному `OptionSet`. Кожен гарячий шлях після цього
(`detach`, `detachMany`, `detachFlagged`) перевіряє біт у цьому закешованому
значенні — `cachedHooks.contains(.releaseDense)` і так далі — ніколи
динамічну диспетчеризацію чи виклик рефлексії. Публічно стан доступний як
`store.supportsCapacityGrowth`. `PackedStore` завжди оголошує `.growDense`
(і `.relocateBatch`); `TagStore` оголошує лише `.growDense`, бо не має
payload, який треба зберігати.

Перед зміною будь-якого масиву світ перевіряє ємність і підтримку зростання
кожного сховища. Якщо хоч одне не підключилося, `reserveCapacity(_:)`
повертає `false`, нічого не змінивши ні у світі, ні в жодному сховищі. Прямого
публічного зростання окремого сховища немає: його ємність не може
розсинхронізуватися з власником через стандартний API.

## Хуки резолвляться один раз, а не виявляються на кожен виклик

Той самий механізм застосовується до кожного опційного хука сховища:

```text
.growDense          -> вмикає World.reserveCapacity()
.relocateBatch       -> вмикає пакетне перенесення payload
.releaseDense         -> вмикає шлях володіння в detach
.clearRelocated        -> очищення дубліката, що лишився після переносу
.clearDense             -> масове очищення на clear()/reset()
```

Спадкоємець оголошує біти, які реалізує, перевизначаючи `var hooks: Hooks`.
Оскільки базовий клас нічого не перевизначає неявно, а `cachedHooks`
резолвиться один раз у `initialize()`, а не перевіряється на кожен виклик,
різниці у вартості рантайму між «цей хук оголошено» і «не оголошено» немає,
крім самої перевірки біта, яка й так потрібна для розгалуження. Це усуває
цілий клас помилок, заради якого й була придумана схема `has_method()` в
оригіналі: булевий прапорець, який можна виставити неправильно (забули
встановити → ресурс тихо протікає; встановили даремно → платите за
непотрібний шлях). У цьому порті окремого прапорця, який міг би розійтися з
перевизначеннями, взагалі немає — `hooks` і перевизначення є одним і тим
самим оголошенням.

## Пакетне знищення

`flushDestroyQueue()` — найдорожча структурна операція: знищити одну
сутність означає відкріпити її від **кожного** зареєстрованого сховища. При
12 сховищах і 10 000 сутностей це 120 000 пар для розгляду.

Реалізація орієнтована на сховища, а не на сутності, і адаптивна:

```text
1. Повторно перевірити ключі з проставленою generation із черги й ущільнити
   тих, хто вижив, у початок того самого масиву — тепер він і слугує списком
   жертв напряму; окремого скретч-буфера немає.
2. Для кожного сховища обрати дешевший обхід:
      count <= reaped * 2   -> detachFlagged(flags)          — O(count)
      інакше                 -> detachMany(queue, count: reaped) — O(reaped)
3. Завершити життєвий цикл: alive = 0, generation = nextGeneration(...),
   повернути id у вільний стек (або перевести слот у retired).
```

**Чому орієнтація на сховища.** `detachMany`/`detachFlagged` резолвлять
`sparseIndex` і `denseEntities` у локальні буферні покажчики один раз, поза
циклом по сутностях (`withUnsafeMutableBufferPointer`), тож пара
сховище/сутність без компонента коштує одне читання масиву без перевірки меж
замість доступу до властивості через `self`. Типова сутність має лише
частину компонентів, тому саме цей шлях пропуску визначає загальну вартість.

**Чому адаптивно.** Сховище з однією сутністю (турель, гравець) не повинно
сканувати 10 000 жертв, щоб її знайти. Обхід власного щільного масиву з
перевіркою байтового прапорця коштує `O(count)` — саме це й робить
`detachFlagged`, а `count` для такого сховища малий незалежно від розміру
черги знищення.

**Чому `detachFlagged()` швидший при масовій смерті.** Знаючи наперед, які
елементи приречені, він не переносить приречений елемент у щойно звільнений
слот лише для того, щоб видалити його наступним кроком: позначені елементи
спершу відрізаються з хвоста — вони взагалі не потребують перенесення — і
лише потім ті, хто вижив, заповнюють решту дірок. Знищення всієї популяції
виконує **нуль** перенесень замість одного на видалення (підтверджено прямо
тестами: `StoreTests.testDetachFlaggedMovesTheMinimum` знищує 64 з 64
сутностей і стверджує рівно нуль викликів `relocateDense`).

Поріг `count <= reaped * 2` — реальна константа в `World.swift`, а не лише
документація: власний коментар у коді пояснює компроміс, який вона кодує —
«сховище виграє, доки воно не набагато більше за список жертв; після
приблизно подвійного розміру зайві ітерації переважують зекономлені
перенесення». Береться консервативне 2x, а не підібране під кожне сховище.

`detachMany()` (за явним списком жертв, без прапорців) не може перенести
менше: маючи лише список жертв, він не має дешевого способу відповісти «чи
приречений і хвостовий елемент теж?» без масиву прапорців, до якого має
доступ `detachFlagged`.

### Пакетне перенесення payload

Коли сховище не має хуків володіння, ніщо не читає payload, поки цикл
виконується, тож кожне перенесення можна записати й застосувати потім, за
один прохід, у тому самому порядку — еквівалентно перемежуванню, але
дозволяючи спадкоємцю резолвити свої масиви один раз на всю операцію, а не
на кожне переміщення. Саме це й робить `PackedStore.relocateDenseBatch`:

```swift
public override func relocateDenseBatch(from: UnsafePointer<Int32>, to: UnsafePointer<Int32>, moveCount: Int32) {
    for column in columns {
        let base = column.storage.baseAddress!
        let stride = column.stride
        for move in 0..<Int(moveCount) {
            memcpy(base.advanced(by: Int(to[move]) * stride),
                   base.advanced(by: Int(from[move]) * stride), stride)
        }
    }
}
```

Резолвінг базового покажчика кожної колонки один раз, а потім прохід по
всіх переміщеннях, замість одного разу на переміщення — саме звідси
пакетний шлях знищення бере більшу частину переваги в швидкості над наївним
циклом `relocateDense` по одному елементу.

Сховище з володінням натомість використовує перемежований шлях:
`releaseDense(_:)` зобов'язаний відпрацювати **до** того, як payload
перезаписано, тож перенесення не можна відкласти й пакетувати так само —
`ComponentStore.detachMany` розгалужується саме на цьому (`.releaseDense`
присутній → перемежування; `.relocateBatch` присутній і без володіння →
пакетно; жодного → запасний варіант по одному переміщенню).

## Перевірка й тестування

`world.validateIntegrity(reportErrors:)` перевіряє:

- `live + free + retired == capacity`;
- унікальність вільного списку й черги знищення;
- що прапорці знищення збігаються з чергою;
- стан «живий» кожної сутності, на яку посилається сховище;
- бієкцію sparse↔dense і межі слотів у кожному сховищі;
- рівність ємності світу й кожного сховища.

Перевірка лінійна й виділяє тимчасові дебаг-буфери, тож не повинна
виконуватися щокадру в продакшні.

```bash
swift test
```

запускає весь набір; `swift test --filter <TestCaseName>` — один. Набір, що
відіграє роль структурних самоперевірок оригінального аддону:

- **`WorldTests`** — виділення й вичерпання, відповідність пакетного
  створення створенню по одному, відкладене знищення, захист ABA
  generational handle (перевикористаний сирий id не воскрешає старий handle;
  handle з одного `World` ніколи не розв'язується в іншому), зростання
  ємності (і handle, і payload переживають його), і `reset()`.
- **`StoreTests`** — swap-remove, суміжність пакетного attach, і —
  диференційна перевірка, на яку спирався оригінал —
  `testDetachManyMatchesRepeatedDetach` пропускає ті самі видалення через
  `detach()` по одному на одному сховищі й через `detachMany()` на
  ідентичному близнюку, після чого стверджує, що фінальне відображення
  сутність → payload ідентичне для обох. Оптимізований шлях зобов'язаний
  бути невідрізним від наївного; диференційний тест проти наївного шляху —
  надійний спосіб це перевірити.
- **`PipelineTests`** — порядок реєстрації як поведінка, пауза як нульовий
  крок, перемикачі системи/фази, `ReaperSystem`, `CapacityPolicySystem`,
  вибір найменшого сховища-драйвера у `View`, матеріалізований кеш `Query` і
  виявлення влучання в кеш.
- **`SpatialAndTimeTests`**, **`DebugTests`** — просторова сітка проти
  еталону грубою силою, годинник з фіксованим кроком, кутова математика, і
  конвеєр recorder/stats/diagnostics (розділи 8, 7, 13).

`relocateDense(from:to:)` неможливо перевірити раз і назавжди для довільного
payload — кожне власне сховище потребує свого тесту на перенесення з
розрізнюваними значеннями в кожному полі, так само як `CountingStore` у
`StoreTests` використовує впізнавані значення float саме для того, щоб
неправильно спрямоване переміщення було видно в assert.

## Рекомендована структура для великої гри

- Один `World` на незалежну симуляцію/матч, а не глобальний singleton.
- Type id — це один enum рівня модуля (`enum ComponentType: Int32`),
  зареєстрований до першої сутності.
- Гарячі, пов'язані між собою дані можна тримати в одному сховищі; опційні
  риси й рідкісні підсистеми виносяться в окремі сховища/теги.
- Сирі id не покидають систем; публічні сервіси, UI і колбеки отримують
  `Handle` чи доменний стабільний id.
- Структурні писачі групуються в чіткі межі фаз.
- Прямі цикли використовуються після профілювання, а не всюди за
  замовчуванням.
- `validateIntegrity(reportErrors: false)` запускається в CI/fuzz і за
  командою дебаг-панелі.
- Шар збереження/мережі серіалізує доменну схему, а не внутрішні щільні
  слоти.
- Сховища лише з даними успадковують `PackedStore`; власний `ComponentStore`
  лишається для нестандартних розкладок чи володіння ресурсами.
- Знищення йде через єдиний `ReaperSystem`, зареєстрований останнім;
  `CapacityPolicySystem` — одразу після нього.
- Залежні від часу системи оголошують `requiresTime = true` замість ручної
  перевірки `delta <= 0`.
- Реакція на появу/смерть іде через опційний журнал змін сховища, а не через
  розкидані по системах колбеки на власний розсуд: читач стоїть одразу
  після жнеця.
- Керована швидкість часу йде через `SimulationClock` із фіксованим кроком;
  сирий `delta × timeScale` розсинхронізує симуляцію на порогах.

## Свідомі обмеження

Aegis не надає archetype-чанків, автоматичного паралельного планувальника,
протоколу rollback/знімків чи універсальної серіалізації. Реактивність є, але
як явний опційний журнал структурних змін, а не подієва/колбек-система:
вартість увімкнення видима, а вимкнений журнал коштує одне розгалуження на
структурну операцію.

Новіші API дають безпечну основу для великої гри, не перетворюючи компактне
ядро на прихований рантайм із непередбачуваною вартістю.
