# 8. Просторовий пошук

---

## 8.1. Задача

«Які об'єкти зараз поруч із точкою X?»

Наївна відповідь — перебрати всіх і порівняти відстань. Це `O(n)` на один
запит. Якщо запитів теж `n` (кожен ворог шукає найближчого сусіда), виходить
`O(n²)`: на 10 000 об'єктів це 100 мільйонів перевірок за кадр. Неприйнятно
вже на кількох тисячах.

`UniformSpatialGrid` розв'язує це поділом простору на однакові комірки.
Об'єкт потрапляє в комірку за своїми координатами, а пошук «хто поруч»
зводиться до перегляду кількох сусідніх комірок замість усього світу.

---

## 8.2. Базове використання

```swift
let grid = UniformSpatialGrid()

// Один раз при складанні:
grid.configure(
    arenaRadius: 130.0,     // межа по площині XZ
    verticalExtent: 0.0,    // 0 = плоский (2D) режим
    cellSize: 10.0,
    entryCapacity: 10000    // максимум записів, які отримає одна rebuild()
)
```

Щокадру, **після** того як усі зрушилися:

```swift
grid.rebuild(entityIDs: entityIDs, points: points, entryCount: entryCount)
```

`entityIDs` — це `[Int32]` (або `UnsafePointer<Int32>` для варіанту без
алокацій), а `points` — `[SIMDVector3]`, власний невеликий value-тип
бібліотеки (`struct SIMDVector3 { var x, y, z: Float }`), а не тип із якогось
UI-фреймворку.

Далі — запити:

```swift
// Найближчий у радіусі, або -1.
let nearest = grid.queryNearest(center: center, radius: 12.0)

// Усі в радіусі. Повертає кількість; самі id — у queryBuffer.
let found = grid.querySphere(center: center, radius: 10.0, resultLimit: 64)
for i in 0..<found {
    let entity = grid.queryBuffer[i]
}
```

> **`queryBuffer` перезаписується наступним запитом.** Читайте його одразу
> або копіюйте потрібне. Результат навмисно потрапляє у властивість
> екземпляра, а не у вихідний `inout`-параметр: так власність і час життя
> результату очевидні, а повернення щойно виділеного масиву алокувало б
> пам'ять на кожен окремий запит.

### Перебудова, а не переміщення

Сітка розрахована на сценарій «усе рухається щокадру»: вона **не підтримує**
точкове переміщення об'єкта — вона перебудовується цілком, із плоскої пари
масивів, кожного разу коли ви викликаєте `rebuild()`. Для симуляції, де майже
все зрушилося, це дешевше, ніж `n` окремих оновлень.

## 8.3. Плоский (2D) режим

```swift
grid.configure(arenaRadius: 130.0, verticalExtent: 0.0, cellSize: 10.0, entryCapacity: 10000)
// verticalExtent = 0
```

Якщо ваша гра відбувається на площині — top-down, RTS, bullet hell,
симуляція в чашці Петрі — передайте `verticalExtent = 0.0`, і сітка
згорнеться в один шар по Y: `dimY` стає `1` замість того, скільки вертикальних
шарів дав би інакше `cellSize`.

Координата Y тоді ігнорується при розкладанні по комірках (перевірки
відстані в `queryNearest`/`querySphere` лишаються повністю тривимірними), а
загальна кількість комірок падає в стільки разів, скільки вертикальних шарів
було б інакше — і це важливо, бо §8.4 нижче показує, що вартість перебудови
визначається саме кількістю комірок, а не лише кількістю записів.

Перевірити режим у рантаймі: `grid.isFlat()`, `grid.getDimensions()`.

---

## 8.4. Найважливіше: підбір `cellSize`

Вартість `rebuild()` — це **`O(записи + ЧИСЛО КОМІРОК)`**, а не тільки
`O(записи)`.

Причина всередині алгоритму: сітка побудована на **counting sort** над
плоскими масивами, і її середній прохід (перетворення гістограми на
префіксні суми) зобов'язаний пройти по **кожній** комірці, включно з
порожніми. Сітка з 10 000 комірок, у якій живе 30 об'єктів, витрачає на цей
прохід майже весь час на порожнечу — це і є той самий механізм, що стоїть за
діагностикою «набагато більше комірок, ніж об'єктів», яку показує панель
інспектора (див. [розділ 13](13-inspektor.md)).

Дві сили тягнуть у різні боки:

- **дрібні комірки** роблять перебудову дорожчою, але прискорюють запити — у
  кожній комірці менше кандидатів;
- **великі комірки** роблять перебудову майже безкоштовною, але запити
  деградують — доводиться перевіряти відстань до купи кандидатів, які
  завідомо не могли опинитися достатньо близько.

### Правило великого пальця

Тримайте `getCellCount()` **співмірним з очікуваною кількістю об'єктів**, а
сам `cellSize` — у **2–4 рази більшим за типовий радіус запиту**.

Або просто спитайте бібліотеку:

```swift
let size = UniformSpatialGrid.suggestCellSize(
    arenaRadius: 130.0,
    verticalExtent: 0.0,      // 0 = плоский
    expectedEntries: 10000,
    typicalQueryRadius: 12.0
)
grid.configure(arenaRadius: 130.0, verticalExtent: 0.0, cellSize: size, entryCapacity: 10000)
```

Формула (`suggestCellSize`) бере «приблизно одна комірка на об'єкт» —
обчислену з площі чи об'єму арени, поділеної на очікувану кількість записів —
і піднімає результат до щонайменше подвоєного радіуса запиту. Це стартова
точка, а не закон: далі профілюйте на власному населенні й характері
запитів.

### Кілька сіток із різними `cellSize`

Це **рекомендований патерн**, а не хитрощі.

Якщо у сцені є і щільна маса дрібних об'єктів, і десяток великих рідкісних,
одна спільна сітка погана для обох: підібрана під щільне населення, вона
марнує перебудову на майже порожню для рідкісних об'єктів область простору,
а підібрана під рідкісне населення робить запити для щільного дорогими.
Заведіть дві:

```swift
// 10 000 юнітів, дрібні комірки: перебудова дорога, але запити швидкі
unitsGrid.configure(arenaRadius: 130.0, verticalExtent: 0.0, cellSize: 6.0, entryCapacity: 10000)

// 30 снарядів, великі комірки: ітерувати 10 000 здебільшого порожніх дрібних
// комірок заради тридцяти записів було б чистою втратою
missilesGrid.configure(arenaRadius: 130.0, verticalExtent: 0.0, cellSize: 40.0, entryCapacity: 64)
```

## 8.5. Позиції разом з ідентифікаторами

Типовий цикл «знайти сусідів і порахувати силу» після `querySphere()`
мусив би для кожного знайденого id ще й дістати його позицію через власне
сховище компонента. Сітка вже має ці позиції, якщо попросити її їх тримати:

```swift
grid.storeQueryPoints = true   // один раз

let found = grid.querySphere(center: center, radius: 10.0, resultLimit: 64)
for i in 0..<found {
    let entity = grid.queryBuffer[i]
    let point = grid.queryPointBuffer[i]        // без зайвого пошуку
    let dx = center.x - point.x
    let dy = center.y - point.y
    let dz = center.z - point.z
}
```

(`SIMDVector3` — це просте значення `{x, y, z: Float}` без власних операторів
векторної математики: віднімання, довжину й нормалізацію пишете самі або
приносите власний математичний тип і конвертуєте на межі.)

`storeQueryPoints` типово вимкнено, щоб виклики, яким потрібні лише id, не
платили за зайвий запис у `queryPointBuffer`.

## 8.6. Власний обхід по комірках

Для нестандартних задач — «усі пари всередині комірки», прохід по всій
сітці бакетами — сітка відкриває свої відсортовані масиви й дозволяє
пройтися по кожній комірці напряму:

```swift
for cell in 0..<grid.getCellCount() {
    let start = Int(grid.getCellStart(cell))
    let end = Int(grid.getCellEnd(cell))
    for s in start..<end {
        let entity = grid.sortedEntities[s]
        let position = grid.sortedPoints[s]
    }
}
```

`sortedEntities` і `sortedPoints` — **тільки для читання** ззовні (`public
private(set)`), за тією ж домовленістю, що й публічні поля сховищ у
[розділі 4](04-komponenty-i-skhovyshcha.md). Публічного API в інший бік — від
довільної точки одразу до індексу її комірки — немає: лише
`queryNearest`/`querySphere` (які роблять це внутрішньо) і обхід за індексом
комірки, як показано вище.

## 8.7. Геометричні припущення

- Світ центрований у нулі по осях **X і Z**: діапазон
  `[-arenaRadius, +arenaRadius]`.
- По **Y** відлік іде вгору від нуля: діапазон `[0, verticalExtent]`.
- Об'єкти **за цими межами не губляться** — вони затискаються у крайні
  комірки, тому запити біля межі арени лишаються коректними.
- `querySphere()` при досягненні `resultLimit` **припиняє пошук**, тому
  обрізаний результат зміщений до комірок, відвіданих першими, а не є
  випадковою вибіркою.

## 8.8. `AngleMath`

Маленький модуль для плавного довороту, повністю незалежний від ECS — просто
три статичні функції над кутами `Float` у радіанах.

```swift
// Довернути current до desired, не більш ніж на maxStep, найкоротшим шляхом.
yaw = AngleMath.approach(yaw, desiredYaw, turnRate * delta)

// Абсолютна найкоротша кутова відстань — «наскільки далеко», без напрямку.
if AngleMath.shortestDelta(yaw, desiredYaw) < firingTolerance {
    fire()
}
```

**Чому це не тривіально.** Наївне
`current += clamp(desired - current, -maxStep, maxStep)` ламається на
переході через ±π. Якщо `current = 3.1`, а `desired = -3.1`, різниця «в лоб»
дорівнює −6.2 рад, хоча найкоротший шлях між цими кутами — усього 0.08 рад
**в інший бік**. `AngleMath.wrap(_:_:_:)` приводить різницю до найкоротшого
еквівалента в `[min, max)` ще до будь-яких подальших обчислень — і
`approach`, і `shortestDelta` побудовані саме на ній.

## Головне з розділу

1. Сітка **перебудовується цілком** щокадру; точкового переміщення немає.
2. Вартість перебудови — `O(записи + КОМІРКИ)`, тому `cellSize` критичний —
   і саме забагато порожніх комірок ловить діагностика сітки в панелі
   інспектора ([розділ 13](13-inspektor.md)).
3. **Плоский режим** (`verticalExtent = 0`) — безкоштовне прискорення для гри
   на площині: менше шарів по Y означає менше комірок за тією ж формулою
   вартості.
4. `suggestCellSize()` дає обґрунтовану стартову точку.
5. Різні за населенням набори об'єктів потребують **різних сіток** із різним
   `cellSize`.
6. `queryBuffer` (і `queryPointBuffer`) перезаписуються наступним запитом.
7. `AngleMath.approach()` — коректний доворот через ±π.
