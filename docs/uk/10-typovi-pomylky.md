# 10. Типові помилки

Довідник у форматі «симптом → причина → виправлення». Більшість помилок із
§10.1 **не дають жодної діагностики взагалі** — саме тому цей розділ існує;
§10.2 охоплює ті, які бібліотека таки повідомляє через `AegisDiagnostics`.

---

## 10.1. Тихі помилки і незахищені креші (найнебезпечніші)

### Після видалення дані перемішалися

**Симптом.** Сутності живі, компоненти на місці, але значення належать не
тим — у ворога чуже здоров'я, снаряд летить не туди. Помилок немає.

**Причина.** Перевизначення `relocateDense(from:to:)` у ручному підкласі
`ComponentStore` забуло поле. При swap-remove на місце видаленого приїхав
останній елемент, але payload саме цього поля лишився на старому місці.

**Виправлення.**

```swift
override func relocateDense(from: Int32, to: Int32) {
    // КОЖНЕ поле, без винятку
    health[Int(to)] = health[Int(from)]
    armor[Int(to)] = armor[Int(from)]
}
```

**Як не наступити знову.** Використовуйте `PackedStore` — його колонки на
основі схеми реалізують перенесення за вас, і ця конкретна помилка стає
структурно неможливою. Якщо сховище має бути ручним, напишіть на нього
окремий тест: створіть дві сутності з **розрізнюваними** значеннями кожного
поля, видаліть першу, перевірте другу (див. `CountingStore` у
`Tests/AegisECSTests/StoreTests.swift` як зразок патерна).

---

### Закешований вказівник на колонку протух

**Симптом.** Після того як популяція виростає за початковий розмір, записи
через раніше отриманий вказівник на колонку `PackedStore` псують чужу
пам'ять або тихо зникають.

**Причина.** `PackedStore.columnF32(_:)` (і подібні) віддають сирий
вказівник, дійсний лише **до зростання ємності світу**
(`World.reserveCapacity()` перевиділяє кожну колонку). Закешований через цей
виклик вказівник — це use-after-free.

```swift
// НЕПРАВИЛЬНО: дістали один раз поза execute(), використовуємо в багатьох кадрах
let x = store.columnF32(0)!
func execute(delta: Float) {
    // ...між кадрами відбулося зростання; x тепер вказує на звільнену пам'ять
}

// ПРАВИЛЬНО: діставайте заново на початку кожного execute()
override func execute(delta: Float) {
    let x = store.columnF32(0)!
    // ...
}
```

---

### Система читає дані минулого кадру

**Симптом.** Зіткнення спрацьовують із запізненням, наведення «відстає» на
кадр, просторовий індекс показує старі позиції.

**Причина.** Система стоїть **не на своєму місці** у порядку реєстрації.

```swift
// НЕПРАВИЛЬНО: індекс будується за старими позиціями
scheduler.addSystem(SpatialIndexSystem())
scheduler.addSystem(MovementSystem())

// ПРАВИЛЬНО
scheduler.addSystem(MovementSystem())
scheduler.addSystem(SpatialIndexSystem())
```

**Порядок реєстрації — це поведінка**
([розділ 5](05-systemy-i-planuvalnyk.md)). Помилки не буде; буде інша гра.

---

### Use-after-free всередині кадру

**Симптом.** Зрідка — «раз на сто кадрів» — дані належать не тій сутності.

**Причина.** Щільний слот закешовано **через** структурну зміну.

```swift
// НЕПРАВИЛЬНО
let slot = positions.indexOf(entity)
world.flushDestroyQueue()                    // swap-remove міг перемістити дані
positions.columnF32(0)![Int(slot)] = 0        // пишемо в чужий компонент
```

**Виправлення.** Діставайте слот заново після будь-якої структурної зміни. І
тримайте `flushDestroyQueue()` **рівно в одній точці кадру** — використовуйте
`ReaperSystem`, зареєстрований останнім (див.
[розділ 3](03-svit-sutnosti-zhyttievyi-tsykl.md)).

> `Handle` лікує протухле **посилання на сутність**, але не протухлий
> **слот**.

---

### Обхід розсипався на ходу

**Симптом.** Частина сутностей пропускається, лічильники не сходяться.

**Причина.** Склад сховища змінюється **посеред обходу цього ж сховища**.

```swift
// НЕПРАВИЛЬНО
for dense in 0..<Int(positions.count) {
    if shouldDie(dense) {
        positions.detach(positions.entityAt(Int32(dense)))   // масив зсунувся
    }
}
```

**Виправлення.** Позначити, а прибрати пізніше, у точці синхронізації:

```swift
for dense in 0..<Int(positions.count) {
    if shouldDie(dense) {
        world.queueDestroy(positions.entityAt(Int32(dense)))
    }
}
```

---

### Force-unwrap колонки крашиться на розбіжності схеми

**Симптом.** Краш (спрацьований force-unwrap `nil`) замість діагностики,
зазвичай одразу після рефакторингу, що змінив порядок `schema` сховища.

**Причина.** `PackedStore.columnF32(_:)` та подібні повертають `nil` при
**будь-якій** розбіжності — неправильний індекс **або** неправильний
`ColumnType` — а не лише при виході за межі. `store.columnF32(0)!` перетворює
відновну помилку схеми на жорсткий краш без жодного контексту, яке саме
сховище чи колонка були не ті.

**Виправлення.** `guard let`/`if let` навколо акцесора, і перевірка
`columnType(_:)`/`columnCount` під час діагностики розбіжності.

## 10.2. Помилки, які бібліотека повідомляє через `AegisDiagnostics`

### `createEntity()` повернув `-1`

**Причина.** Світ заповнений: `getFreeCount() == 0`. `-1` — це
`kInvalidEntity`.

**Виправлення.** Або підніміть початкову ємність, або використовуйте
[`CapacityPolicySystem`](07-chas-podii-yemnist.md#73-ємність-і-політика-зростання)
для проактивного зростання, або знищуйте активніше. І **завжди перевіряйте
результат на `kInvalidEntity`** — це не виняткова ситуація, а нормальний
стан, під який API спроєктовано.

---

### `registerStore()` повернув `false`

Три можливі причини, кожна зі своїм повідомленням:

| Повідомлення | Причина |
|---|---|
| `"World: schema locked by the first createEntity(); register stores earlier"` | Сховище реєструється **після** створення першої сутності. Реєструйте всі сховища до створення чогось. |
| `"World: component type N is already registered"` | Продубльована константа id типу. |
| `"World: store is already registered under another type or in another world"` | Той самий об'єкт сховища реєструють удруге. |

---

### `reserveCapacity()` повернув `false`

**Причина.** Або запитана ємність не більша за поточну, або якесь
зареєстроване сховище не оголошує `.growDense` у своїх `hooks`.

**Виправлення.** Додайте хук у ручне сховище:

```swift
override var hooks: Hooks { [.growDense] }
override func growDense(previousCapacity: Int32, newCapacity: Int32) {
    while values.count < Int(newCapacity) { values.append(0) }
}
```

`PackedStore` і `TagStore` завжди оголошують `.growDense`. Перевірити в
рантаймі: `store.supportsCapacityGrowth`.

---

### `"clearRelocated without releaseDense"`

**Причина.** `hooks` ручного сховища оголошує `.clearRelocated`, але не
`.releaseDense`. Ви реалізували очищення дубліката, що лишає по собі
перенесення, але ніколи не звільняєте те, чим володів видалений слот — це
майже завжди означає **витік ресурсу**.

**Виправлення.** Реалізуйте обидва разом — див.
[§4 про компоненти з володінням ресурсами](04-komponenty-i-skhovyshcha.md).

---

### `"one instance cannot be registered in two schedulers"` / `"the same system object was registered twice"`

**Причина.** Один екземпляр `System` додано у два різні `Scheduler`
(перше повідомлення, з `System.assignPhase`), або той самий екземпляр додано
двічі в один планувальник (друге, з `Scheduler.addSystem`).

**Виправлення.** Створіть окремий екземпляр на кожен конвеєр; реєструйте
кожен екземпляр один раз.

---

### `"system X did not finish describing its access"` / `"did not declare access to type N"`

**Причина.** `View.validateOwnerAccess`/`Query.validateOwnerAccess` —
діагностика лише метаданих, що **не впливає на виконання** — знайшла
систему, яка або ніколи не викликала `completeAccessMetadata()`, або
використала тип через `View`/`Query`, якого не оголосила через
`declareRead`/`declareWrite`/`declareStructuralWrite`.

**Виправлення.** Додайте `.completeAccessMetadata()` після оголошення
доступу й оголосіть кожен тип, якого справді торкаються view системи — або
просто не викликайте методи валідації, якщо не користуєтесь цим
інструментарієм.

---

### `"PackedStore: no columns declared"`

**Причина.** `PackedStore(schema: [])` — порожня схема.

**Виправлення.** Використовуйте `TagStore` для компонента, який узагалі не
несе payload.

## 10.3. Проблеми продуктивності

### Кадр «просідає» рівно тоді, коли багато хто гине

**Причина.** Знищення коштує `O(жертви × сховища)`
([розділ 9](09-produktyvnist.md)).

**Виправлення.**
- Об'єднайте дрібні спеціалізовані сховища там, де це має сенс.
- Розтягніть масову смерть на кілька кадрів.
- Для повного очищення беріть `World.reset()`, а не масовий `queueDestroy` +
  flush.

---

### Перебудова сітки з'їдає весь кадр

**Причина.** Невдалий `cellSize`: вартість — `O(записи + КОМІРКИ)`.

**Виправлення.** `UniformSpatialGrid.suggestCellSize()`, плоский режим для
гри на площині, окремі сітки для населень дуже різного розміру. Див.
[§8.4](08-prostorovyi-poshuk.md#84-найважливіше-підбір-cellsize).

---

### `Query` перебудовується щокадру

**Причина.** Якесь сховище-учасник щокадру змінює склад — часто це тег, який
щось причіпляє й віддирає кожен кадр.

**Перевірка:**

```swift
print(query.rebuildCountValue)   // росте на 1 щокадру?
```

**Виправлення.** Або приберіть мінливий тип зі складу обов'язкових/виключених
у запиті, або перейдіть на `View` / прямий цикл — кеш, що завжди
промахується, тільки додає роботи поверх того, чого мав уникнути.

---

### Обхід повільніший, ніж очікувалося

**Причина.** Виклик акцесора колонки або `View.matches(_:)` усередині циклу
замість того, щоб винести вказівник/sparse-масив один раз перед ним.

**Виправлення.** Див.
[§9.1](09-produktyvnist.md#91-struct-of-arrays-а-не-обєкт-на-сутність) і
[§9.6](09-produktyvnist.md#96-view-і-query-не-алокують-у-гарячому-шляху).

## 10.4. Помилки при прискоренні часу

### Симуляція «перестрибує» події на високій швидкості

**Симптом.** При `timeScale = 50` те, що мало б відбуватися періодично,
відбувається рідше, ніж треба; швидкі снаряди пролітають крізь цілі.

**Причина.** Сирий `delta` за кадр, помножений на масштаб, дає один
величезний крок симуляції замість багатьох дрібних.

**Виправлення.**
[`SimulationClock`](07-chas-podii-yemnist.md#71-simulationclock--фіксований-крок-і-масштаб-часу) —
викликайте `advance(realDelta:)` і виконуйте один крок фіксованого розміру
на кожен субкрок, який вона поверне.

---

### Гра зависає при прискоренні

**Причина.** «Спіраль смерті»: кожен субкрок вимагає реального часу на
обчислення, тож достатньо великий `timeScale` змушує кожен кадр видавати
більше субкроків, ніж попередній встиг завершити, без обмеження.

**Виправлення.** `clock.maxSubsteps` (типово `8`) обмежує це. Слідкуйте за
`clock.droppedSubsteps` — якщо воно постійно росте, машина справді не тягне
запитаний `timeScale`.

---

### На паузі щось усе одно рухається

**Причина.** Система ніколи не встановила `requiresTime = true`, тож
`Scheduler` і далі викликає її на кроці нульової довжини.

**Виправлення.**

```swift
final class MovementSystem: System {
    override init() {
        super.init()
        systemName = "Movement"
        requiresTime = true
    }
}
```

---

### Сутності накопичуються в черзі під час паузи

**Причина.** `ReaperSystem` отримав `requiresTime = true`.

**Виправлення.** Не робіть цього. `ReaperSystem` навмисно **не** встановлює
`requiresTime` — сутності, поставлені в чергу на знищення до паузи, все одно
мають бути прибрані, поки гра на паузі.

## 10.5. Швидка діагностика

Коли незрозуміло, що взагалі відбувається:

```swift
// 1. Чи цілий світ?
assert(world.validateIntegrity(), "world integrity check failed")

// 2. Що з населенням?
print("live=\(world.getLiveCount()) free=\(world.getFreeCount()) "
    + "pending=\(world.getPendingDestroyCount()) load=\(world.getLoadFactor())")

// 3. Чи узгоджені сховища зі світом?
print("positions=\(positions.count) hostiles=\(hostileTag.count)")

// 4. Куди йде час?
for i in 0..<scheduler.systemCount {
    print("\(scheduler.getSystemName(i))  \(Int(scheduler.getAverageTimingUsec(i))) us")
}

// 5. Чи правильно зібраний конвеєр?
scheduler.validatePipeline(world: world)
```

## Чекліст перед тим, як шукати баг деінде

- [ ] Ручні сховища реалізують `relocateDense(from:to:)` для **кожного**
      поля?
- [ ] `flushDestroyQueue()` викликається **рівно в одному місці** — один
      `ReaperSystem`, зареєстрований останнім?
- [ ] Дані індексуються **щільним слотом**, а не id сутності?
- [ ] Порядок систем відповідає порядку залежностей за даними?
- [ ] Щільні слоти й вказівники на колонки `PackedStore` ніколи не
      кешуються через структурну зміну чи зростання через
      `reserveCapacity()`?
- [ ] Склад сховища лишається незмінним, поки триває обхід цього ж сховища?
- [ ] Результат `createEntity()` перевіряється на `kInvalidEntity`?
- [ ] Системи, залежні від часу, встановлюють `requiresTime = true`?
