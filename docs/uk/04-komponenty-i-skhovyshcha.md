# 4. Компоненти і сховища

Сховище (`store`) — це контейнер даних одного типу компонента для всіх
сутностей. Саме тут живе вся розкладка пам'яті, заради якої існує ECS.

---

## 4.1. Як влаштоване сховище

Кожне сховище — це **sparse set** із двох масивів у протилежних напрямках:

```
sparseIndex[entity] → щільний слот, або -1, якщо компонента немає
denseEntities[slot] → якій сутності належить цей слот
```

Плюс масиви **самих даних**, індексовані **тим самим щільним слотом**.

```swift
let slot = positions.indexOf(entity)      // entity 42 → slot 5
if slot != -1 {
    print(positionX[Int(slot)])           // дані шукаємо за 5, а не за 42
}
```

> **Найчастіша помилка новачка:** індексувати масив даних ідентифікатором
> сутності. `positionX[42]` — це майже завжди чужий компонент або сміття. Дані
> адресуються **слотом**, не id.

Три поля базового `ComponentStore` навмисно оголошені як `public internal(set)`:
`sparseIndex`, `denseEntities` і `count`. Писати їх може тільки бібліотека, але
читати — будь-хто ззовні, і саме для того, щоб система один раз узяла їх у
локальну змінну (або відкрила через `withUnsafeBufferPointer`) і далі індексувала
напряму, без виклику методу й без зайвої непрямої адресації на кожен елемент.
Поза модулем вважайте їх **тільки для читання**.

## 4.2. `PackedStore` — рекомендований спосіб

```swift
enum EnemyColumn: Int32 { case position, health, speed, tint }

let enemies = PackedStore(schema: [.vec3, .float32, .float32, .vec4])
world.registerStore(enemies, typeID: ComponentType.enemy.rawValue)
```

Це все. Ви один раз оголошуєте **схему типів колонок** — виділення пам'яті,
зростання ємності та перенесення даних при видаленні реалізує базовий клас.

У Swift немає рефлексії за іменем поля, як у старого `track(&"name")`, тому
колонка ідентифікується **індексом**, а не назвою. Дайте індексам власні імена
через `enum: Int32`, як вище, і передавайте його `rawValue` там, де очікується
індекс.

**Підтримувані типи колонок** (`ColumnType`):

| Case | Що зберігає | Розмір |
|---|---|---|
| `.uint8` | 1 байт | 1 |
| `.int32` / `.float32` | 4 байти | 4 |
| `.int64` / `.float64` / `.vec2` | 8 байтів | 8 |
| `.vec3` | 3 × float32 | 12 |
| `.vec4` | 4 × float32 — також форма кольору | 16 |

**Колонки-об'єкта не існує.** Компонент, якому потрібно володіти екземпляром
класу, ресурсом чи будь-чим іншим із власною ідентичністю, не може бути полем
`PackedStore` — дивіться [4.6](#46-компоненти-з-володінням-ресурсами).

### Чому це не повільніше

```swift
let hp = enemies.columnF32(EnemyColumn.health.rawValue)!
for slot in 0..<enemies.count {
    hp[Int(slot)] -= poisonDamage
}
```

`columnF32` (і сусідні `columnF64`, `columnI32`, `columnI64`, `columnU8`)
повертають сирий вказівник на сховище цієї колонки — отримати його означає
проіндексувати невеликий внутрішній список колонок, а не шукати, тож викликати
це один раз на початку `execute()` і далі індексувати вказівник у циклі не
коштує нічого зайвого. Кожен метод повертає `nil`, якщо індекс поза межами
**або** колонка насправді іншого типу, тож розбіжність схеми проявляється як
`nil`, який можна перевірити, а не як переінтерпретовані байти — примусове
розгортання (`!`) безпечне, тільки коли ви впевнені, що схема збігається.

Колонки `vec2`/`vec3`/`vec4` поки що не мають власного типізованого акцесора.
Дістаньтеся до них через нетипізований вказівник `columnData(_:)` і прив'яжіть
тип самостійно:

```swift
let position = enemies.columnData(EnemyColumn.position.rawValue)!
    .assumingMemoryBound(to: SIMDVector3.self)
position[Int(slot)] = SIMDVector3(x, y, z)
```

Узагальнена робота відбувається лише під час виділення пам'яті та видалення, і
навіть там `PackedStore` не програє ручному сховищу: він оголошує хук
`.relocateBatch`, тож пакетне знищення дістає сховище кожної колонки **один
раз** на всю операцію, а не на кожен переміщений елемент (див.
[4.5](#45-необовязкові-хуки)).

### Корисні члени

```swift
store.columnCount              // скільки колонок оголосила схема
store.columnType(_ index:)     // ColumnType? для цієї колонки
store.clearSlot(_ slot:)       // записує нуль у всі колонки цього слота
```

Викликайте `clearSlot()` одразу після `attach()`, якщо у сховища є колонки, які
шлях створення не завжди заповнює: слоти перевикористовуються, і свіжо
приєднаний компонент інакше почне життя з тим, що лишив попередній власник
слота.

## 4.3. `TagStore` — компонент без даних

Іноді системі не треба знати про сутність нічого, крім самого факту
приналежності до категорії: «це ворог», «це снаряд», «це можна підібрати».

```swift
let hostileTag = TagStore()
world.registerStore(hostileTag, typeID: ComponentType.hostile.rawValue)

hostileTag.attach(entity)
if hostileTag.has(entity) { /* ... */ }

// Найцінніше — щільний обхід усієї категорії:
for i in 0..<hostileTag.count {
    let enemy = hostileTag.entityAt(i)
}
```

Тег не має масивів payload, тому видалення взагалі нічого не переносить.
`TagStore` іде далі й перевизначає `detachMany`/`detachFlagged` напряму версією,
що не викликає `relocateDense` навіть жодного разу, — це найдешевше сховище в
бібліотеці.

---

## 4.4. `ComponentStore` — ручне сховище

Нижчий рівень. Потрібен, коли розкладка нестандартна: компонент, що володіє
екземпляром класу (4.6), поле-бітова маска, або payload, який треба переносити
нетривіально.

Спадкоємець **зобов'язаний** перевизначити два методи. Обидва в базовому класі
за замовчуванням викликають `fatalError`, тож забути хоч один — не тиха
поведінка, а гарантований крах під час першого ж використання сховища:

```swift
final class CustomStore: ComponentStore {
    var packedFlags: ContiguousArray<Int32> = []

    // 1. Виділити своє сховище під ємність світу.
    override func reserveDense(_ capacity: Int32) {
        packedFlags = ContiguousArray(repeating: 0, count: Int(capacity))
    }

    // 2. Перенести дані при swap-remove.
    override func relocateDense(from: Int32, to: Int32) {
        packedFlags[Int(to)] = packedFlags[Int(from)]
    }
}
```

> **Тонша версія тієї самої класичної помилки все ще можлива.** Якщо взагалі не
> перевизначити `relocateDense`, крах станеться одразу й недвозначно. Але ручне
> сховище з кількома полями, яке перевизначає `relocateDense` і забуває
> скопіювати лише одне з них, ламається так само, як стара помилка завжди
> ламалась: swap-remove тихо лишає застаріле значення саме цього поля, і ніде
> нічого не друкується. Це рівно та помилка, яку `PackedStore` (4.2) прибирає
> конструктивно — він генерує `relocateDense` зі схеми, тож там немає коду по
> полях, який можна забути.

## 4.5. Необов'язкові хуки

У Swift немає рефлексії на кшталт `has_method()`, тому спадкоємець
**оголошує**, які необов'язкові хуки він реалізує, перевизначаючи
`var hooks: Hooks` — `OptionSet`:

```swift
final class CustomStore: ComponentStore {
    override var hooks: Hooks { [.growDense, .relocateBatch] }
    // ...
}
```

| Хук | Навіщо | Перевизначення |
|---|---|---|
| `.growDense` | Дозволяє `world.reserveCapacity()`. Має зберегти всі дані в `0..<count`. | `growDense(previousCapacity:newCapacity:)` |
| `.relocateBatch` | Пакетне перенесення: дістати сховище один раз на всю операцію, а не на кожне переміщення. | `relocateDenseBatch(from:to:moveCount:)` |
| `.releaseDense` | Звільнити те, чим володіє слот, перед перезаписом. | `releaseDense(_:)` |
| `.clearRelocated` | Очистити дублікат у слоті, звідки дані переїхали. | `clearRelocatedDense(_:)` |
| `.clearDense` | Масове очищення при `clear()` / `world.reset()`. | `clearDense(activeCount:)` |

`PackedStore` уже оголошує `.growDense` і `.relocateBatch`; `TagStore` оголошує
`.growDense`. Жодному з них не треба нічого додаткового з вашого боку, щоб
підтримати `world.reserveCapacity()`.

> **Реальна діагностика, а не порада зі стилю.** Оголошення `.clearRelocated`
> без `.releaseDense` повідомляється в момент реєстрації сховища: слот-джерело
> буде очищено, але те, чим він володів, ніколи насправді не звільниться.

### Зростання ємності для ручного сховища

```swift
override func growDense(previousCapacity: Int32, newCapacity: Int32) {
    while packedFlags.count < Int(newCapacity) { packedFlags.append(0) }   // зберігає [0, count)
}
```

Перевірити підтримку можна так:

```swift
if store.supportsCapacityGrowth { /* ... */ }
```

Якщо хоча б одне зареєстроване сховище не оголошує `.growDense`,
`world.reserveCapacity()` поверне `false`, **не змінивши нічого**.

## 4.6. Компоненти з володінням ресурсами

Схема `PackedStore` містить лише примітивні числові та векторні колонки (4.2),
тож компонент, який має володіти екземпляром класу, файловим дескриптором чи
будь-чим іншим із власною ідентичністю, потребує ручного `ComponentStore`. ARC у
Swift звільняє посилання в момент, коли на нього більше ніхто не вказує, тож
«звільнити» слот — це просто присвоїти йому `nil`, але **порядок**, у якому це
відбувається, важить не менше, ніж для вручну звільнюваного ресурсу:

```swift
final class TextureStore: ComponentStore {
    private var textures: [CGImage?] = []

    override var hooks: Hooks { [.growDense, .releaseDense, .clearRelocated, .clearDense] }

    override func reserveDense(_ capacity: Int32) {
        textures = Array(repeating: nil, count: Int(capacity))
    }
    override func growDense(previousCapacity: Int32, newCapacity: Int32) {
        while textures.count < Int(newCapacity) { textures.append(nil) }
    }
    override func relocateDense(from: Int32, to: Int32) {
        textures[Int(to)] = textures[Int(from)]
    }

    // Викликається на слоті, який ВИДАЛЯЄТЬСЯ, ДО перенесення даних.
    override func releaseDense(_ slot: Int32) {
        textures[Int(slot)] = nil
    }
    // Викликається на слоті, ЗВІДКИ дані переїхали.
    // Тут ТІЛЬКИ очищаємо дублікат — володіння вже перейшло на нове місце.
    override func clearRelocatedDense(_ slot: Int32) {
        textures[Int(slot)] = nil
    }
    // Масове очищення при clear() / world.reset().
    override func clearDense(activeCount: Int32) {
        for slot in 0..<Int(activeCount) { textures[slot] = nil }
    }
}
```

**Порядок має значення.** `detach()` спочатку викликає `releaseDense()` на
слоті, що видаляється, і лише потім переносить payload з останнього слота та
викликає `clearRelocatedDense()`. Переплутати їх — означає або витік посилання
(його ніколи не обнулили, тож ARC ніколи його не звільнить), або очищення
слота раніше, ніж дані з нього насправді переїхали. Забути `releaseDense` для
слота, що ненадовго тримав сильне посилання, тримає той об'єкт живим стільки,
скільки якийсь непов'язаний пізніший компонент випадково опиниться в цьому
перевикористаному слоті, — реальний і важкопомітний витік.

## 4.7. Основні операції

```swift
let slot = store.attach(entity)     // ідемпотентно; -1 при переповненні або невалідному id
store.detach(entity)                // безпечно, навіть якщо компонента немає

store.has(entity)                   // Bool
store.indexOf(entity)               // слот або -1
store.entityAt(slot)                // сутність, якій належить слот
store.count                         // скільки компонентів
store.clear()                       // спорожнити без алокацій
```

> `has`, `indexOf` і `entityAt` позначені `@inline(__always)` і **навмисно не
> перевіряють межі** — це примітиви гарячого циклу. Передати сюди id
> неіснуючої сутності — помилка викликального коду. Структурні входи (`attach`,
> `detach` та їхні пакетні форми) межі перевіряють, бо виконуються значно
> рідше.

### Пакетні операції

```swift
let first = store.count
let attached = store.attachMany(ids, count: idCount)
// нові слоти: [first, first + attached)

let removed = store.detachMany(ids, count: idCount)
```

`attachMany` пропускає сутності, у яких компонент уже є, тому `attached` може
бути меншим за `idCount`.

## 4.8. Як розкласти дані по сховищах

Практичне питання: одне велике сховище чи багато маленьких?

**Тримайте разом те, що читається разом.** Якщо система руху щокадру читає
позицію і швидкість, є сенс покласти їх в одне сховище: тоді не потрібен пошук
через `sparseIndex`, обхід іде по одному щільному масиву.

**Розділяйте те, що використовується рідко або окремо.** Компонент, який має
кожна десята сутність, у спільному сховищі змусив би решту дев'ять носити
незаповнені колонки — і, що гірше, зайняв би місце в лініях кешу гарячого
циклу.

**Ознаки-прапорці виносьте в теги.** «Оглушений», «невразливий», «у воді» — це
`TagStore`, а не `Bool`-колонка у великому сховищі: тег дає щільний список саме
тих, кого це стосується.

Приклад розкладки для гри:

| Сховище | Колонки | Хто читає |
|---|---|---|
| `Transform` | position, yaw | майже всі системи |
| `Locomotion` | velocity, speed | рух, наведення |
| `Health` | current, max | урон, смерть |
| `MissileLauncher` | cooldown, range | тільки система стрільби (мало сутностей) |
| `HostileTag` | — | спавн, пошук цілей |
| `StunnedTag` | — | рух (виключення) |

---

## Головне з розділу

1. Дані адресуються **щільним слотом**, а не id сутності.
2. Для звичайних даних беріть **`PackedStore`** — оголосіть схему типів колонок,
   жодного шаблонного коду і жодної втрати швидкості.
3. `TagStore` — для ознак без даних.
4. Ручне `ComponentStore` **зобов'язане** перевизначити `reserveDense` і
   `relocateDense` — пропустити хоч один означає негайний крах (`fatalError`),
   але частково правильне перевизначення все одно може тихо зіпсувати дані.
5. Необов'язкові хуки **оголошуються**, а не визначаються автоматично:
   перевизначте `var hooks`, і базовий клас викличе рівно те, що ви оголосили.
6. Сховища з володінням ресурсом реалізують `.releaseDense` **і**
   `.clearRelocated` — порядок їх виклику критичний, а в `PackedStore` для
   цього випадку взагалі немає типу колонки.
7. Разом читається — разом і зберігайте; рідкісне й окреме виносьте.
