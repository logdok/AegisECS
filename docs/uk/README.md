# Aegis ECS — посібник користувача

Aegis ECS — це компактний **ECS-рушій на чистому Swift**, що постачається як
Swift Package. Це зроблений з нуля Swift-порт ECS-рушія, спершу написаного на
чистому GDScript для Godot 4 — дизайн (sparse-set сховища, swap-remove,
відкладене знищення, планувальник із фіксованим порядком реєстрації)
переноситься без змін; нові тут лише мова й інтеграція з платформою. Він
створений для симуляцій, де тисячі й десятки тисяч об'єктів оновлюються
щокадру: юніти, снаряди, частинки ігрової логіки, натовп, bullet hell,
популяційні симуляції.

- **Без залежностей.** Чистий Swift, збирається через Swift Package Manager —
  без сторонніх пакетів.
- **Без прихованих алокацій** у сталому циклі кадру. Пам'ять росте лише через
  явний бар'єр.
- **Жодного екземпляра класу на ігровий об'єкт.** Дані живуть у пласких,
  суцільних колонках (`PackedStore`).
- **Жодного шаблонного коду.** `PackedStore` генерує все сховище — пам'ять,
  зростання й перенесення при swap-remove — зі схеми колонок.
- **Пакетні структурні операції.** Спавн і знищення — один виклик, а не N.
- **Вбудований інспектор.** Статистика кадру, пошук винуватця ривків і
  діагностика типових помилок — підключається кількома рядками, з опційною
  SwiftUI-панеллю в окремому продукті.
- **Безпечні посилання.** Упаковані generational handle захищають від ABA.
- **Працює всюди, де працює Swift.** Жодного платформозалежного коду в ядрі;
  сьогоднішня межа — iOS 16 / macOS 13 (див.
  [Package.swift](../../Package.swift)).

## Як читати цей посібник

Розділи впорядковані так, щоб їх можна було читати підряд, але кожен
самодостатній.

**Якщо ви ніколи не чули про ECS** — почніть з розділу 1. Він пояснює не «як
викликати методи цієї бібліотеки», а **чому** такий підхід взагалі існує і яку
проблему розв'язує. Це найважливіший розділ: без нього решта виглядатиме як
дивний спосіб писати звичайний код.

одразу до розділу 2, а потім до розділу 4: сховища тут влаштовані як sparse set,

## Шість правил безпеки

Стисла пам'ятка. Кожне правило розгорнуто у своєму розділі, а симптоми порушень
зібрані в [розділі 10](10-typovi-pomylky.md).

1. **Сирий `Entity` (`Int32`) — для гарячого циклу, `Handle` (`Int64`) — для
   посилань між кадрами.** Handle не можна писати у save/network дані як
   стабільний ідентифікатор — його тег світу прив'язаний до одного запуску
   процесу.
2. **Структурні зміни — лише на визначених точках синхронізації.** Не посеред
   системи; не можна кешувати щільний слот чи покажчик колонки `PackedStore`
   через цю межу.
3. **Реалізуйте `relocateDense(from:to:)`** у ручному сховищі — забуте поле
   тихо змішає дані. Або беріть `PackedStore`, де помилитися неможливо.
4. **Покажчик колонки `PackedStore` дійсний лише до наступного зростання
   ємності світу.** Отримуйте його заново всередині `execute()`, а не
   кешуйте між кадрами.
5. **`View`/`Query` оновлюються до того, як прочитано структурну зміну**, і
   склад сховища не можна міняти посеред обходу цього ж сховища.
6. **Пауза — це `delta == 0`**, а не пропуск кадру. Оголошуйте `requiresTime
   = true`.

## Перевірка, що все працює

```bash
swift build
swift test
```

`swift test` запускає власний набір `XCTest` пакета
(`Tests/AegisECSTests/*.swift`) — ті самі тести, якими зафіксована поведінка
порту: swap-remove лишає щільний масив невпорядкованим, `detachFlagged`
виконує теоретичний мінімум переміщень, вичерпана generation назавжди
переводить слот у retired, і так далі (див.
[ARCHITECTURE.md](ARCHITECTURE.md#validation-and-testing), що покриває кожен
файл тестів). Придатний для CI як є, без окремого headless-прапорця, який
треба пам'ятати.

[Розділ 11](11-povnyi-pryklad.md) розбирає повну робочу симуляцію по
шматочках; він написаний прямо в посібнику, а не постачається як окрема
виконувана ціль-приклад, тож читайте його, а не намагайтеся виконати як є.

## Два продукти, і що можна додати чи не додавати

Пакет надає два бібліотечні продукти з однієї залежності Swift Package:

| Продукт | Що всередині | Залежить від |
|---|---|---|
| `AegisECS` | Ядро (`World`, сховища, системи, `Scheduler`, `ReaperSystem`, `CapacityPolicySystem`), просторовий пошук, годинник з фіксованим кроком, кутова математика, і headless-шар діагностики | нічого |
| `AegisECSInspectorUI` | `InspectorPanelView`, SwiftUI-панель розробника з [розділу 13](13-inspektor.md) | `AegisECS` |

Headless-ціль — сервер, перевірка бюджету в CI, фонова симуляція — залежить
лише від `AegisECS` і ніколи не підключає SwiftUI. Додавайте
`AegisECSInspectorUI` лише там, де справді хочете показати панель; ціль, яка
її ніколи не додає, взагалі не компілює посилання на `InspectorPanelView`,
тож вирізати нічого не потрібно.

На відміну від оригінального аддону, чиї модулі були незалежними файлами, які
можна було видаляти теку за текою з проєкту Godot, ядро `AegisECS` — це один
скомпільований Swift-модуль: `Core/`, `Debug/`, `Math/`, `Spatial/` і `Time/`
збираються разом як одна ціль. Якщо ваш застосунок справді ніколи не
торкається просторової сітки чи годинника з фіксованим кроком, невикористаний
код усе одно компілюється — але це кілька невеликих файлів без залежностей, і
лінкер все одно прибирає непотрібні символи з вашого бінарника.

### Про конфлікт імен

Типи Swift обмежені модулем, а не реєструються в єдиному глобальному просторі
імен, як це робили оголошення `class_name` оригінального аддону.
`import AegisECS` вносить у видимість `World`, `System`, `Scheduler`,
`ComponentStore` та решту в межах вашого файлу; якщо ваш застосунок уже
оголошує тип з однією з цих назв, розрізняйте через повне
`AegisECS.World`, а не перейменовуйте щось у бібліотеці.

## Словник

Терміни, які зустрічаються в усіх розділах.

| Термін | Значення |
|---|---|
| **Сутність (entity)** | Просто ціле число — ідентифікатор. Не об'єкт, не нода, не клас. |
| **Компонент (component)** | Чисті дані, прив'язані до сутності. Позиція, здоров'я, швидкість. |
| **Система (system)** | Чиста логіка, що читає й пише компоненти. Без власного стану. |
| **Світ (world)** | Розподільник ідентифікаторів сутностей і реєстр сховищ. |
| **Сховище (store)** | Контейнер даних одного типу компонента для всіх сутностей. |
| **Щільний слот (dense slot)** | Індекс усередині щільного масиву сховища. Не дорівнює id сутності. |
| **Sparse set** | Структура з двох масивів, що дає і щільний обхід, і пошук за O(1). |
| **Swap-remove** | Видалення за O(1): останній елемент переїжджає на місце видаленого. |
| **Structural change** | Зміна складу: створення, знищення, attach, detach. |
| **Handle** | Безпечне посилання на сутність, що переживає кадри. |
| **Broadphase** | Структура для швидкої відповіді «хто поруч». |
