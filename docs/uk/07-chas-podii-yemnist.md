# 7. Час, події, ємність

Три інструменти, що закривають типові потреби симуляції: керована швидкість
часу, реакція на появу й зникнення сутностей, і зростання світу під
непередбачуване населення.

---

## 7.1. `SimulationClock` — фіксований крок і масштаб часу

### Проблема

Передавати сирий `delta` кадру прямо в симуляцію можна лише доти, доки цей delta
малий. Щойно з'являється можливість **прискорити час**, усе ламається: при
масштабі 50× кадр у 16 мс перетворюється на крок у 800 мс.

І тоді все, що просувається по порогу, **перестрибує** через кілька порогів за
одне оновлення:

- клітина, що ділиться у віці 10, за один крок проживає вік 0 → 12 і ділиться
  один раз замість двох;
- снаряд «телепортується» крізь ціль, бо точкова перевірка влучання не бачить
  проміжних позицій;
- кулдаун у 0.2 с спрацьовує один раз замість чотирьох.

Симуляція не просто йде швидше — вона **дає інший результат**. І на повільнішій
машині — інший ще раз, бо там delta більший.

### Розв'язок

`SimulationClock` накопичує реальний час, множить його на масштаб і повідомляє,
скільки **однакових** відрізків фіксованого розміру в ньому вміщується.

```swift
let clock = SimulationClock()
clock.fixedStep = 1.0 / 60.0      // довжина одного відрізка симуляції
clock.timeScale = 4.0             // прискорення
clock.maxSubsteps = 8             // запобіжник (це типове значення)
```

### Використання з фазами (рекомендовано)

```swift
func tick(delta: Float) {
    let steps = clock.advance(realDelta: delta)

    scheduler.beginFrame()
    for _ in 0..<steps {
        scheduler.executePhase(Phase.simulation, delta: clock.fixedStep)
    }
    // Презентація — рівно один раз на кадр, з РЕАЛЬНИМ delta.
    scheduler.executePhase(Phase.presentation, delta: delta)
}
```

**Зверніть увагу на два різні delta.** Симуляція отримує `fixedStep`,
презентація — реальний час кадру. Проганяти весь конвеєр через цикл суб-кроків
означало б робити роботу рендера N разів на кадр без жодної користі.

Коли `steps == 0` (пауза, або накопичилося менше за один відрізок), фаза
презентації все одно виконується — саме це тримає застосунок намальованим.

### Використання без фаз

```swift
let steps = clock.advance(realDelta: delta)
if steps == 0 {
    scheduler.executeAll(delta: 0)                  // тільки системи без requiresTime
} else {
    for _ in 0..<steps {
        scheduler.executeAll(delta: clock.fixedStep)
    }
}
```

Це прямо продовжує [розділ 5](05-systemy-i-planuvalnyk.md#pause): пауза — це
`delta == 0`, і саме це видає `advance(realDelta:)`, коли `timeScale == 0` — нуль
суб-кроків, тож `executeAll`/`executePhase` того кадру взагалі не бачать
ненульового delta.

### Запобіжник від «спіралі смерті»

`maxSubsteps` — не просто обмеження. Це захист від відомої патології: якщо один
кадр був повільним, накопичилося більше часу; проганяти все накопичене зробить
кадр іще повільнішим, що накопичить іще більше — і застосунок зависає назавжди.

Понад `maxSubsteps` надлишок **відкидається**, а не відкладається: симуляція
ненадовго йде в сповільненому темпі замість того, щоб заблокуватися.

```swift
clock.droppedSubsteps     // скільки відрізків відкинуто всього
clock.isSaturated()       // чи впирається просто зараз
```

Постійно зростаючий `droppedSubsteps` означає, що машина не тягне запитаний
`timeScale`. Це чесний сигнал, а не помилка.

### Інтерполяція

Якщо частота симуляції нижча за частоту кадрів, рух виглядає ступінчастим.
`getAlpha()` повертає частку невитраченого відрізка в `[0, 1)`:

```swift
let alpha = clock.getAlpha()
let drawnPosition = previousPosition.lerp(currentPosition, alpha)
```

### Повний API

```swift
clock.advance(realDelta:) -> Int32     // викликати РІВНО раз на кадр
clock.fixedStep                        // довжина відрізка
clock.timeScale                        // 0 = стоп, 1 = реальний час, 50 = швидко
clock.maxSubsteps                      // запобіжник
clock.paused                           // заморозити, не втрачаючи акумулятор
clock.getLastSubsteps()
clock.getAlpha()
clock.isSaturated()
clock.getEffectiveTimeScale(realDelta:) // фактична швидкість проти запитаної
clock.elapsedSimulated                 // точна сума, без дрейфу
clock.totalSubsteps
clock.droppedSubsteps
clock.reset()                          // на перезапуску рівня
```

> `elapsedSimulated` зростає рівно на `fixedStep` за відрізок, тому він
> **точний**, на відміну від суми дробових delta, яка накопичує похибку.

## 7.2. Журнал змін — реакція на появу і смерть

Бібліотека навмисно не має подій «компонент додано / видалено»: сповіщення на
кожну структурну зміну при десятках тисяч сутностей коштувало б дорожче за саму
роботу.

Натомість є **журнал структурних змін**, який вмикається окремо на кожному
сховищі — він живе на самому `ComponentStore`, тож працює однаково для
`PackedStore`, `TagStore` чи ручного сховища.

```swift
enemies.trackChanges = true
```

Доки прапорець вимкнений (типово), він коштує **одне розгалуження на структурну
операцію**, тобто фактично нічого. Увімкнення лениво виділяє масиви журналу при
першому зверненні.

### Читання журналу

```swift
final class DeathEffectSystem: System {
    private var context: Context!

    override init() {
        super.init()
        systemName = "DeathEffects"
        _ = completeAccessMetadata()
    }

    override func setup(world: World, context: Any?) {
        self.context = context as? Context
    }

    override func execute(delta: Float) {
        let enemies = context.enemies

        for i in 0..<Int(enemies.addedCount) {
            spawnAppearEffect(enemies.addedEntities[i])
        }
        for i in 0..<Int(enemies.removedCount) {
            spawnDeathEffect(enemies.removedEntities[i])
        }

        context.world.clearChangeLogs()
    }
}
```

### Куди ставити систему-читача

**Одразу після `ReaperSystem`.** На цей момент:

- `addedEntities` містить усе, що з'явилося цього кадру;
- `removedEntities` містить усе, що загинуло цього кадру (жнець уже відпрацював).

```swift
scheduler.addSystem(SpawnSystem())
scheduler.addSystem(CombatSystem())
scheduler.addSystem(ReaperSystem(world: world))
scheduler.addSystem(DeathEffectSystem())     // ← читає журнал і чистить його
```

### Правила

- Дійсні префікси — `0..<addedCount` і `0..<removedCount`. Самі масиви можуть
  бути більшими, решта — сміття.
- **Порядок не визначений.** Не спирайтеся на нього.
- Сутність, створена й знищена в одному кадрі, потрапить в **обидва** журнали.
  Це коректно.
- `clear()` і `world.reset()` **не пишуть** окремі видалення — вони піднімають
  прапорець `changeLogOverflowed`. Проганяти всю популяцію через журнал при
  перезапуску рівня — не те, чого хоче викликальний код; читач має перевіряти
  цей прапорець і трактувати його як «вважай, що змінилося все», а не довіряти
  неповному `removedEntities`.
- `world.clearChangeLogs()` чистить журнали всіх сховищ, у яких відстеження
  увімкнене.

### Вартість

Увімкнення виділяє два буфери, які ростуть подвоєнням, доки не досягнуть розміру
типової кадрової плинності. Далі — стала пам'ять і по одному запису в масив на
структурну операцію.

## 7.3. Ємність і політика зростання

### Явне зростання

```swift
if world.reserveCapacity(200_000) {
    resizeMyRenderBuffers(200_000)
}
```

Світ і **усі** зареєстровані сховища ростуть разом; наявні сирі id, handle і
щільні слоти лишаються дійсними.

Це **алокуючий бар'єр**. Викликайте його на екрані завантаження або на явній
межі фаз — ніколи посеред обходу систем.

Якщо хоча б одне зареєстроване сховище не оголошує хук `.growDense` (див.
[розділ 4](04-komponenty-i-skhovyshcha.md)), виклик поверне `false`, **не
змінивши нічого**. `PackedStore` і `TagStore` підтримують його завжди.

> Бібліотека може збільшити лише **власні** буфери. Все, що ваш застосунок
> виділив паралельно — рендер-буфер, батчі фізики, мережеві масиви — ваша
> відповідальність; саме для цього призначений
> `CapacityPolicySystem.onCapacityGrown`.

### Автоматична політика

Для симуляції з вибуховим ростом населення — поділ клітин, ланцюгова реакція,
хвилі — чекати на `world.createEntity() == -1` пізно: спавни вже почали
губитися.

```swift
let policy = CapacityPolicySystem(world: world)
policy.growThreshold = 0.8          // рости при 80% заповнення
policy.growthFactor = 1.5           // нова ємність = стара × 1.5
policy.maximumCapacity = 500_000    // стеля; 0 = без обмеження
policy.checkIntervalFrames = 30
policy.onCapacityGrown = { previous, next in
    renderBuffer.resize(next)
    print("світ виріс: \(previous) → \(next)")
}

scheduler.addSystem(ReaperSystem(world: world))
scheduler.addSystem(policy)          // ← ОДРАЗУ після жнеця
```

**Реєструйте одразу після жнеця** або на іншій явній межі фаз: зростання
переалокує всі буфери, тому жодна система не має тримати щільний слот чи
псевдонім масиву через цей виклик.

Примусова перевірка, якщо ви наперед знаєте про майбутній сплеск:

```swift
policy.growNow()
```

Діагностика: `policy.growthCount`, `policy.lastGrowthCapacity`.

### Скільки ємності брати одразу

Пам'ять на сутність — якщо порахувати за реальною шириною полів:

- **світ:** 19 байт службових даних на сутність (`alive`, `destroyFlag`,
  `retired` — по 1 байту; `freeIDs`, `destroyQueue`, `destroyGeneration`,
  `generations` — по 4 байти);
- **кожне сховище:** 8 байт (`sparseIndex` + `denseEntities`, по 4 байти) плюс
  розмір payload.

Для 100 000 сутностей і 10 сховищ по 16 байт payload (чотири колонки `float32`)
це близько `100k × (19 + 10 × (8 + 16)) ≈ 25.9 МБ`. Виділити наперед більше, ніж
треба, майже завжди дешевше, ніж рости під час гри.

## Головне з розділу

1. `SimulationClock` робить симуляцію **відтворюваною** при будь-якій швидкості
   часу; сирий delta цього не дає.
2. Симуляція отримує `fixedStep`, презентація — реальний `delta`.
3. `maxSubsteps` — запобіжник від спіралі смерті; відкинуті відрізки видно через
   `droppedSubsteps`.
4. Журнал змін (`trackChanges` на `ComponentStore`) — це «події появи й смерті»;
   читач ставиться одразу після жнеця й сам чистить журнал.
5. `reserveCapacity()` — алокуючий бар'єр; лише на безпечній межі.
6. `CapacityPolicySystem` росте **заздалегідь**, а не після втрати спавнів.
